# dnsfilter benchmark

End-to-end measurement of dnsfilter as a black box: UDP queries in, answers out. It shows
what a query costs when it passes the filter and goes upstream, and when the filter answers it
itself.

```
loadgen (dnsperf) ──► dnsfilter :15354 ──► upstream (Knot DNS) :15353
```

## Usage

Requires Docker with Compose and [just](https://github.com/casey/just).

```sh
cd benchmark
just bench
```

Settings live in `config/bench.env`. `just bench` builds the images, generates the data set and
starts Knot and dnsfilter. It then checks that both answer correctly, runs the closed-loop matrix
and the ramps, and writes the report to `results/<date>/`; `results/latest` points to the last
run. The containers are removed at the end, including after a failure or Ctrl+C.

## Layout


| Path                            | Content                                                                                             |
| ------------------------------- | --------------------------------------------------------------------------------------------------- |
| `compose.yaml`                  | services: `data` (one-shot generator), `upstream`, `dnsfilter`, `loadgen`, `profile`                |
| `config/bench.env`              | all settings                                                                                        |
| `config/knot.conf`, `test.zone` | upstream configuration, mounted into the Knot container                                             |
| `docker/`                       | `loadgen`: Debian trixie with dnsperf, kdig, gawk, gnuplot, perf. `dnsfilter`: from this repository |
| `scripts/bench.sh`              | runs inside `loadgen`: data generation, matrix, ramps, report, profiling                            |
| `scripts/dnsperf.awk`           | turns one dnsperf output into a CSV row                                                             |
| `scripts/plots.gp`              | charts                                                                                              |


Images: `cznic/knot:3.6` (official), and dnsperf/resperf 2.14 and perf 6.12 from Debian
packages. `flamegraph.pl` comes from [FlameGraph](https://github.com/brendangregg/FlameGraph),
pinned by commit and checksum, since Debian does not package a flame graph renderer.

## Environment

All containers use the host network and talk over loopback. That keeps Docker NAT and veth out
of the measured path: every scenario has the same transport, and the only difference is
dnsfilter.

Each service is pinned to its own CPUs (`FILTER_CPUS`, `UPSTREAM_CPUS`, `LOADGEN_CPUS`).
dnsfilter is single-threaded and gets one core. Knot gets four cores with four UDP workers, so it
is never the bottleneck. The defaults assume a 16-core / 32-thread CPU where CPU *n* and *n + 16*
are SMT siblings, so the three sets sit on different physical cores. Adjust them for other
machines.

## Data set

Generated by the `data` service, deterministic for the same settings:


| File            | Content                                                  |
| --------------- | -------------------------------------------------------- |
| `blocklist.txt` | `FILTER_SIZE` names `ads-N.block.test`                   |
| `pass.txt`      | `QUERY_COUNT` names `www.site-N.pass.test A`             |
| `block.txt`     | `QUERY_COUNT` names `www.ads-R.block.test A`, random `R` |
| `mixed.txt`     | `BLOCK_RATIO` percent from `block.txt`, the rest pass    |


A passed name misses the blocklist on all four suffix lookups. A blocked name hits on the second
lookup (`ads-R.block.test`), so the hierarchical match is exercised.

The Knot zone has a wildcard under `pass.test` only. Every passed name resolves to `192.0.2.1`.
A `block.test` name that leaks past dnsfilter gets `NXDOMAIN`.

## Scenarios


| Scenario   | Target    | What it measures                                                |
| ---------- | --------- | --------------------------------------------------------------- |
| `baseline` | Knot      | dnsperf and Knot alone, the floor for `pass`                    |
| `pass`     | dnsfilter | full forwarding path: parse, filter miss, forward, match answer |
| `block`    | dnsfilter | parse, filter hit, synthesized answer, upstream never contacted |
| `mixed`    | dnsfilter | `BLOCK_RATIO` percent blocked, the rest forwarded               |


The cost dnsfilter adds to a forwarded query is the difference between `pass` and `baseline`.

## Load



### Closed-loop matrix (dnsperf)

dnsperf keeps exactly `-q` queries in flight. It sends the next one as soon as an answer arrives
or a query times out. That number is the matrix axis (`OUTSTANDING`, default `1 8 32 128`):

- `-q 1` is pure sequential latency: one query at a time, no queueing anywhere.
- Higher levels add concurrency until dnsfilter's single thread saturates. Past that point, more
in-flight queries only add queueing delay; by Little's law, latency ≈ outstanding / qps.

Each point is measured `REPEATS` times. One run is a `WARMUP`-second dnsperf run whose result is
discarded, then a `DURATION`-second measured run. The loop order is repeat → outstanding →
scenario. Slow drift such as heating or background load then shows up as variance, not as a bias
against one scenario.

Queries go over `CLIENTS` UDP sockets from one dnsperf thread. They are type `A`, with no EDNS
and RD set. The query file restarts from the top when it runs out. Nothing caches: dnsfilter
has no cache, and Knot answers from the zone. An answer later than `TIMEOUT` seconds counts as
lost.

### Open-loop ramp (resperf)

For every scenario in `RAMP_SCENARIOS`, resperf raises the send rate linearly from 0 to
`RAMP_MAX_QPS` over `RAMP_TIME` seconds, regardless of answers. It reports the highest rate
dnsfilter sustained. `ramp.png` shows where the answered rate falls away from the target rate.
Set `RAMP_MAX_QPS` to roughly twice the expected limit.

## Report


| File             | Content                                                                                                     |
| ---------------- | ----------------------------------------------------------------------------------------------------------- |
| `summary.csv`    | one row per `(scenario, outstanding)`: means over repeats, qps standard deviation, total lost, invalid runs |
| `runs.csv`       | every run: sent, completed, lost, qps, latency avg/p50/p90/p99/p99.9/max, RCODEs, `valid`                   |
| `ramp.csv`       | maximum sustained rate per ramp scenario                                                                    |
| `throughput.png` | qps by in-flight queries, error bars are the standard deviation                                             |
| `latency.png`    | p50 and p99 by in-flight queries                                                                            |
| `ramp.png`       | resperf ramps                                                                                               |
| `meta.txt`       | commit, CPU, kernel, dnsperf version, settings                                                              |
| `raw/`           | unmodified dnsperf and resperf output                                                                       |


`qps` is answered queries divided by run time, as reported by dnsperf. Percentiles come from the
dnsperf latency histogram, which has 1 µs buckets.

## Errors and validity

qps counts answered queries only. dnsfilter never sends an error answer of its own. On a failure
it logs the error and drops the packet. dnsperf then reports the query as lost after `TIMEOUT`.
The lost query also holds its in-flight slot for that long, so failures lower qps and raise
tail latency; they never inflate the numbers.

Answers that dnsfilter forwards from upstream keep their RCODE, and dnsperf would count a
`SERVFAIL` as answered. So a run is marked `valid=no` when:

- nothing was answered,
- any query was lost, or
- any answer is not `NOERROR`. In this setup that means an upstream failure, or a blocked name
that leaked to Knot and came back as `NXDOMAIN`.

The matrix does not stop at an invalid run. The report is written in full, then the invalid
runs are printed and `just bench` exits with status 1. A non-zero exit means "do not trust
these numbers". If the servers do not answer the sanity check before the matrix, the run is
aborted.

## Profiling

```sh
just profile              # scenario pass, 32 queries in flight
just profile block 128
```

`just profile` shows where dnsfilter spends its CPU time under load. It builds dnsfilter with
the `profiling` Cargo profile (release with debug info, not stripped) and starts the same data,
Knot and dnsfilter as `just bench`. The `profile` service then runs the sanity check, a
`WARMUP`-second dnsperf run, and one `PROFILE_DURATION`-second dnsperf run while `perf record`
samples dnsfilter at `PROFILE_FREQ` Hz with call stacks.

| File (in `results/profile-<date>/`, `results/latest-profile`) | Content                                       |
| -------------------------------------------------------------- | --------------------------------------------- |
| `flamegraph.svg`                                               | flame graph, open in a browser                |
| `report.txt`                                                   | top objects and functions from `perf report`  |
| `stacks.folded`                                                | collapsed stacks the flame graph is drawn from |
| `dnsperf.txt`                                                  | dnsperf output of the profiled run            |
| `meta.txt`                                                     | as in the benchmark, plus scenario and level  |

In the flame graph the width of a frame is its share of samples, callers are below callees.
Kernel frames are orange, user space frames red. Click a frame to zoom, Ctrl+F to search. With
fat LTO almost all of dnsfilter is inlined into `dnsfilter::main::{closure#0}`; inlined
functions still show up as their own frames. `report.txt` has three parts: self time per object
(the kernel and its modules are in brackets, `[vdso]` is user space), self time per function,
and total time of dnsfilter functions including their callees.

Things to know when reading it:

- The `[unknown]` libc frames right above `entry_SYSCALL_64` are glibc's `__syscall_cancel`
  wrappers that issue the syscall. Debian's libc has no symbols for them.
- `nf_*` and `nft_*` frames are the host firewall (Docker's rules), which also sees loopback
  traffic. They are part of the environment and are in the benchmark numbers too.
- Samples in JIT-compiled BPF code have no symbol and may be attributed to the nearest module
  symbol, e.g. `rapl_check_unit_atom`.
- perf costs a little throughput, so compare the qps in `dnsperf.txt` only with other profiles.

User stacks are unwound from DWARF debug info (`--call-graph dwarf`), so dnsfilter needs no frame
pointers and the unwinding goes through glibc, which has none. Debian trixie's perf 6.12 is used:
the 7.x perf from backports unwinds with libdw only and produces broken user stacks here.

No host settings are changed. The `profile` container runs as root with `CAP_SYS_ADMIN` and
`CAP_SYSLOG` in dnsfilter's PID namespace: `CAP_SYS_ADMIN` overrides `perf_event_paranoid`
(kernel samples included) and lets perf enter dnsfilter's mount namespace to read its binary;
`CAP_SYSLOG` exposes kernel addresses in `/proc/kallsyms`, unless the host has
`kernel.kptr_restrict = 2`. The recipe fails if the profile has no symbolized kernel frames or
no dnsfilter symbols.

## Caveats

- Everything goes over loopback on one machine. The numbers show the software cost of
dnsfilter, not what a real network adds.
- dnsperf has a single thread. At high `OUTSTANDING`, `baseline` may be limited by the generator
rather than by Knot. If the `baseline` p50 stays far below outstanding / qps, dnsperf is not
keeping all queries in flight.
- For stable numbers, set the `performance` CPU governor and keep the machine otherwise idle.
Compare commits on the same machine and settings, and use `qps_sd` to judge whether a
difference is noise.
